Press Enter Studio

A config-driven framework for producing the 7-video series What Happens When You Press Enter? Visuals and narration are separate components, joined only by cue IDs, so you can change a title in JSON or re-record one paragraph and rebuild without touching anything else.

Builds on the series roadmap (6 Nov) and the travel-theme guidelines. Nothing here is built yet; this is the plan to agree on first.

The series as a journey

The running prompt "Write a short poem about the rain" is the traveller. Each video is a stop, stamped on its passport, and every video opens with "Next stop: …!". The journey diagram from the roadmap becomes the route map, with the current stop highlighted. Stop names and stamps live in config, so you can rename them freely.

What the framework must do

RequirementHow the design meets it
Change a title or any text in JSON and rebuildAll series and episode content lives in validated JSON and Markdown. Components only receive props and never hold text.
Visuals and audio are separate componentsTwo independent tracks. Visuals point at cue IDs, never at seconds. A timeline resolver joins them at build time.
Retake one paragraph and inject itEach paragraph is a cue with its own audio take. Drop in a new take and only that cue, and the one segment that uses it, are reprocessed.
Change the script and stay in syncEach cue stores a hash of its text. Edited cues are flagged stale, then re-voiced (TTS) or queued for you to re-record.
Programmatic and semi-automatedOne CLI (press …) runs every step. Every artifact is cached by content hash, so a rebuild redoes only what changed.

Architecture

Read left to right: you author files in a Git repo, the audio and visual tracks build in parallel, the timeline resolver joins them, and the assembler produces every output format. The review studio at the bottom closes the loop.

audio flowvisual flowtiming joinreview feedback
The key idea: audio decides time, visuals follow cues. No animation is ever placed at "2:41". It is placed at c07, or at a word inside it (c07@ids). The resolver turns cue durations into frames on every build. Re-record a paragraph 3 seconds longer, and everything after it moves automatically. Because each segment renders separately with its own relative timing, only the changed segment is re-rendered.

The config files

Four kinds of file, all plain text in Git, so every change has a history and can be reverted.

series.json: written once, used by every video

{
  "title": "What Happens When You Press Enter?",
  "subtitle": "How ChatGPT, Claude and Gemini Really Work",
  "runningPrompt": "Write a short poem about the rain",
  "theme": "travel",
  "voice": { "provider": "kokoro", "voice": "af_heart", "speed": 1.0 },
  "stops": [
    { "ep": 3, "name": "Token City", "stamp": "TOKEN CITY · STAMPED" }, …
  ],
  "template": ["passport", "hook", "routeMap", "core+", "tryIt",
               "blooper?", "myth", "useIt", "recapNext"]   // + = one or more, ? = optional
}

episode.json: which segments, which components, which props

{
  "id": "ep03", "title": "Tokenization: How Text Becomes Numbers",
  "question": "How does a computer read my words?",
  "segments": [
    { "id": "passport", "component": "PassportStamp" },
    { "id": "subwords", "component": "TokenBlocks",
      "props": { "text": "$runningPrompt", "showIdsAt": "c07@ids" } },
    { "id": "tryIt", "component": "TryIt",
      "props": { "task": "Ask it to count the r's in strawberry" }, "short": true }
  ]
}

script.md: the narration, one cue per paragraph

Written as normal prose. A cue ID tags each paragraph, a heading names the segment it belongs to, and {@name} marks a word an animation can wait for.

## subwords
[c06] On the left is our prompt. On the right, its tokens.
[c07] The model never sees the word rain. It only sees numbers, like {@ids}4,812.
[c08] Pause here and guess: how many tokens is "strawberry"?

audio.lock.json: generated, never hand-edited

"c07": { "textHash": "9f2c…", "take": "takes/c07/v3.wav", "source": "human",
         "duration": 5.84, "marks": { "ids": 4.12 }, "status": "ok" }

Retaking one paragraph

The workflow you asked for, step by step:

  1. You change the wording of paragraph c07 in script.md, or decide you dislike how it sounds.
  2. press status ep03 shows c07 as stale: its text hash no longer matches its take.
  3. Either let TTS re-voice it (press voice ep03 c07), or record yourself in the cue board, or drop a file: press take ep03 c07 my-retake.wav.
  4. The take is trimmed and loudness-matched to −16 LUFS so it sounds like its neighbours, then aligned to find the {@ids} word time.
  5. press render ep03: the resolver recomputes the timeline, only the subwords segment re-renders, and the rest comes from cache.
  6. The new master, captions, Shorts and description timestamps are regenerated. Old takes stay in takes/c07/, so you can switch back.

Choosing the video engine

The visual track needs an engine that renders deterministic frames from code. Three realistic options:

Recommended

Remotion

React components rendered to video, frame by frame.

  • Props validated by schema and editable in its preview studio
  • Composition length can be computed from audio, which matches our timing model
  • Mature: CLI, Node API, parallel and cloud rendering
  • License: free for individuals and companies of up to 3 people; larger companies need a paid license
Alternative

Motion Canvas

TypeScript animation library built around voice-over sync.

  • MIT licensed, free for any use
  • Good editor for syncing to a voice track
  • Smaller ecosystem; headless batch rendering is less mature
Already built

Our GSAP engine

What rendered the Unit 1 NLP video: GSAP scenes captured by a headless browser.

  • Works today, fully ours, no license question
  • Already audio-driven per beat
  • No preview studio; we would build all the tooling

The audio track is independent of this choice. The Kokoro voice pipeline, take management and lock file work the same with any engine.
